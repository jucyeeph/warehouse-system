# 260515 文件夹优先改造方案

## 背景

当前仓库到货系统会遇到多种真实现场问题：

1. 箱码二维码损坏，扫不出来。
2. 采购单条码打印不清晰，扫不出来。
3. 员工操作前端不规范，例如把采购单码扫到箱码位置。
4. 后端为了避免上传失败，会把缺失或异常信息写入兜底目录，例如 `data/uploads/unknown/`。
5. 兜底目录不符合到货日期/箱码结构，后续 DB 同步和管理员前端展示可能都看不到或显示错误。

对 Julthee 来说，数据库不是可直接维护的东西；真正可理解、可检查、可修复的是文件夹。因此本系统后续原则应调整为：

> 文件夹结构是根本，数据库只是文件夹结构的索引和展示缓存。

## 总原则

### 1. 文件夹是主数据源

所有 PO 图片最终必须落在一个明确、可人工理解的文件夹结构中。

数据库应从文件夹扫描/同步得到信息，而不是让文件夹被隐藏在数据库逻辑之后。

### 2. 正常流程禁止静默进入 `unknown`

员工正常开箱上传时，如果箱码、采购单号、到货日期不明确，系统不能偷偷保存到 `unknown`。

应当直接阻止并提示员工处理，例如：

- 请先扫描箱码，不要扫描采购单码。
- 该箱码还没有到货日期，请先做“到货登记”。
- 采购单号格式不正确，请重新扫描或手动输入。

### 3. 异常情况也要有明确结构

现实中确实会有扫不出来的情况，但不能混乱保存。异常也必须进入固定结构，方便管理员后续整理。

## 建议文件夹结构

根目录保持：

```text
data/uploads/
```

### A. 正常情况：已知到货日期 + 已知箱码 + 已知采购单

```text
data/uploads/2026-05-12/20260407DSH061/POMCMP030456_20260407DSH061_20260513_101337.jpg
```

含义：

- `2026-05-12`：到货日期
- `20260407DSH061`：箱码
- `POMCMP030456`：采购单号
- `20260513_101337`：拍照/上传时间

这是所有正常数据的标准格式。

### B. 箱码扫不出来，但知道到货日期

```text
data/uploads/2026-05-12/No box code/POMCMP030456_NOBOXCODE_20260513_101337.jpg
```

用途：员工知道今天是哪批到货，但箱码二维码坏了。

要求：

- 员工前端必须明确选择“箱码扫不出来”。
- 必须选择到货日期。
- 可选填写备注或拍箱子外观照片。
- 管理员前端应有“待补箱码”列表。
- 管理员补上箱码后，系统把文件移动到：

```text
data/uploads/2026-05-12/20260407DSH061/POMCMP030456_20260407DSH061_20260513_101337.jpg
```

### C. 采购单扫不出来 / 没有 PO paper，但知道到货日期 + 箱码

不再单独创建 `No PO code` 子文件夹。只要箱码明确，资料就直接留在该箱码文件夹里；是否缺 PO code、是否配件箱、是否手工清点，都通过文件夹备注和文件名备注表达。

```text
data/uploads/2026-05-12/20260501DSH030（配件箱、手工清点）/
└── NOPO_20260501DSH030_20260513_101337（配件箱、手工清点）.jpg
```

用途：

- 采购单条码打印不清晰，无法识别 PO code。
- 工厂没有放 PO paper。
- 这箱是配件箱，不对应单独 PO paper。
- 员工只能拍手工清点照片。

要求：

- 必须已有箱码。
- PO code 为空时，必须选择备注原因。
- 备注写进箱码文件夹名和文件名。
- 管理员补上采购单号后，可以把文件重命名为标准格式，并按需要去掉文件夹备注：

```text
data/uploads/2026-05-12/20260501DSH030/POMCMP030456_20260501DSH030_20260513_101337.jpg
```

### D. 没有 PO paper / 配件箱 / 手工清点照片

现实中有些箱子可能没有 PO paper：

- 工厂忘记放 PO paper
- 这箱是某个产品的配件，不需要 PO paper
- PO paper 破损严重，无法识别
- 员工只能拍手工清点的箱内物品清单

这类情况不能当成错误上传，也不能进 `unknown`。它仍然属于这个箱子的开箱资料。

#### D1. 有箱码时

文件夹名允许在箱码后追加备注：

```text
data/uploads/2026-05-12/20260501DSH030（配件箱、手工清点、采购单破损）/
└── NOPO_20260501DSH030_20260513_101337（配件箱、手工清点、采购单破损）.jpg
```

注意：备注里不要用 `/`，因为 `/` 在文件系统里会变成下一级目录。前端可以显示 `配件箱/手工清点/采购单破损`，但写入文件夹时统一替换成中文顿号 `、`。

提交规则：

- unboxing 模块中，采购单码可以为空，但不能直接静默上传。
- 如果 PO code 为空并点击上传，弹出“未填写采购单码”提醒窗口。
- 提醒窗口必须要求员工：
  - 从下拉备注中选择至少一个原因；或
  - 点击取消返回填写 PO code。
- 没选择备注不能提交。
- 备注写入箱码文件夹名和文件名，便于 Julthee 只看文件夹也知道原因。

建议备注选项：

- 工厂未放 PO paper
- 配件箱
- 手工清点
- 采购单破损
- 采购单打印不清
- 其他（必须填写说明）

#### D2. 没有 PO paper，也没有 box code

极端情况下，如果没有 PO paper，也没有 box code，也仍然可以跑通，但必须落到明确异常目录：

```text
data/uploads/2026-05-12/No box code/NOPO_NOBOXCODE_20260513_101337（配件箱、手工清点）.jpg
```

要求：

- 必须选择到货日期。
- 必须选择备注。
- 必须拍照：箱内物品清单/箱子外观/手写说明，至少一张。
- 管理员前端把它列入“待补箱码 / 无 PO 资料”队列。

### E. 到货时箱码扫不进去，开箱时箱码扫进去了

这种情况很常见：到货环节可能因为角度、光线、网络、员工操作等原因没有成功入库，所以到货日期文件夹里还没有这个箱码目录；但开箱时二维码又能扫出来。

处理规则：

1. 员工在 unboxing 模块扫到有效箱码。
2. 后端发现该箱码没有 arrival record / 没有到货日期文件夹。
3. 前端不要拒绝上传，也不要进入 `unknown`。
4. 前端弹出“该箱码还没有到货登记”的窗口，要求员工选择到货日期。
5. 到货日期必须来自下拉栏：
   - 优先列出系统已有到货日期；
   - 可以提供“今天”快捷项；
   - 不允许自由输入混乱日期。
6. 员工确认后，后端补创建 arrival record，并创建标准箱码目录：

```text
data/uploads/2026-05-12/20260501DSH029/
```

7. PO paper 照片正常保存到该箱码目录：

```text
data/uploads/2026-05-12/20260501DSH029/POMCMP030456_20260501DSH029_20260513_101337.jpg
```

这类情况本质上是“补到货登记 + 开箱上传”合并操作，不能交给 Renalyn，也不能进 `No box code`。

### F. 到货时箱码能扫，开箱时箱码扫不出来

这种情况说明箱码文件夹通常已经存在：

```text
data/uploads/2026-05-12/20260501DSH030/
```

员工开箱时如果扫不出箱码，不应该重新进入 Renalyn 的流程，也不应该直接扔到 `No box code`。应走“无法扫码开箱”流程：

1. 员工点击“箱码扫不出来，但已到货登记”。
2. 选择到货日期。
3. 系统列出该到货日期下“已到货但未开箱/未上传 PO 照片”的箱码候选。
4. 员工选择对应箱码，页面显示：
   - 到货日期
   - 箱码
   - 现有文件夹路径
5. 员工拍照上传 PO paper 或手工清点照片。
6. 文件仍然保存到原来的箱码文件夹。

只有在员工无法确认是哪个已到货箱码时，才进入：

```text
data/uploads/2026-05-12/No box code/
```

### G. Error PO Paper 独立错误采购单模块

`Error PO Paper` 不是到货系统的一部分，不放在某个到货日期下面；它直接放在 `data/uploads/` 根目录下，作为 Renalyn 更新 BigSeller 时的错误 PO 模块单独管理。

```text
data/uploads/Error PO Paper/
├── POMCMP030456_error_20260513_141440.jpg
└── Solved/
    └── solved_20260513_141440《POMCMP030456_20260501DSH029_20260513_101337.jpg》.jpg
```

含义：

- `data/uploads/Error PO Paper/`：待处理的错误 PO paper 图片。
- `data/uploads/Error PO Paper/Solved/`：已经处理完成的错误 PO paper 图片。
- 它们不混入：
  - `data/uploads/<到货日期>/...`
  - `data/uploads/<到货日期>/<箱码>/...`
- 到货系统只管理到货、箱码、正常 PO 图片。
- 错误 PO 模块单独展示、单独处理、单独归档。

处理规则：

1. Renalyn 更新 BigSeller 失败时，上传错误 PO 图片到：

```text
data/uploads/Error PO Paper/POMCMP030456_error_20260513_141440.jpg
```

2. 管理员/负责人处理完成后，移动到：

```text
data/uploads/Error PO Paper/Solved/solved_20260513_141440《POMCMP030456_20260501DSH029_20260513_101337.jpg》.jpg
```

3. 如果需要和正常到货 PO 图片配对，配对关系可以存在 DB 或元数据里，但文件本身仍然留在 `Error PO Paper` 模块，不移动进到货日期目录。

### H. 到货日期未知

正常员工流程不应允许这种情况。

如果管理员确实要补传，可进入专门的管理员异常入口：

```text
data/uploads/_needs_arrival_date/20260513/POMCMP030456__NOBOX__20260513_101337.jpg
```

含义：

- `_needs_arrival_date`：待补到货日期
- `20260513`：上传日期，不是到货日期

管理员补齐到货日期和箱码后，再移动到标准结构。

### I. 废弃 `unknown`

后续新上传不再创建：

```text
data/uploads/unknown/
```

历史已有 `unknown` 可以保留，但管理员前端应提供“历史异常文件整理”入口，帮助把它们移动到标准结构或异常结构。

## 员工前端防呆规则

### 1. 开箱模式必须先锁定箱码

员工进入开箱上传时：

1. 先扫箱码。
2. 后端校验箱码格式。
3. 后端确认该箱码已有到货日期。
4. 页面显示：
   - 当前箱码
   - 到货日期
   - 状态：已锁定
5. 只有锁定后才能继续上传采购单照片。

如果扫到的是 `POMCMP` 开头的采购单号，应阻止：

```text
你扫到的是采购单号，不是箱码。请先扫描箱子二维码。
```

### 2. 采购单号必须校验

采购单号必须符合：

```text
POMCMP + 6位数字
```

例如：

```text
POMCMP030456
```

不符合则禁止提交。

### 3. 扫不出来要走明确异常按钮

不要让员工随便空着提交。

前端按钮建议：

- 箱码扫不出来
- 箱码扫不出来，但已到货登记
- 采购单扫不出来
- 没有 PO paper / 配件箱 / 手工清点
- 重扫箱码
- 重扫采购单

每个异常按钮都进入固定异常结构，而不是进入 `unknown`。

### 4. PO code 为空时必须选择备注

unboxing 模块里，PO code 可以为空，但不能直接提交。

如果员工点击上传时 PO code 为空：

1. 弹出“未填写采购单码”提醒窗口。
2. 窗口提供备注下拉/多选：
   - 工厂未放 PO paper
   - 配件箱
   - 手工清点
   - 采购单破损
   - 采购单打印不清
   - 其他
3. 员工必须选择备注或取消。
4. 没有 PO code 且没有备注时，禁止提交。
5. 备注写入文件夹/文件名，例如：

```text
20260501DSH030（配件箱、手工清点、采购单破损）
```

### 5. 提交前确认

提交前展示清楚：

```text
到货日期：2026-05-12
箱码：20260407DSH061
采购单：POMCMP030456
照片：1张
```

员工点确认后才上传。

## 第一阶段员工端输入模块规范

### Receiving & Unboxing

#### arrival scan 模块

- `box_code` 必须符合固定箱码格式，例如：`YYYYMMDD + 类型码 + 3位序号`。
- 示例：`20260501DSH030`、`20260407LCC003`。
- 如果扫到 `POMCMP030456`，提示：`你扫到的是采购单号，不是箱码，请扫描箱子二维码。`
- 如果格式不符合，提示：`箱码格式不正确，请重扫或联系管理员。`
- 格式错误时不创建到货记录，也不创建文件夹。

#### unboxing 模块

- `box_code` 和 `PO code` 必须各自走自己的格式校验。
- `box_code` 不允许填 PO code。
- `PO code` 不允许填 box code。
- 开箱时箱码扫不出来，但到货时已经扫过：走“箱码扫不出来，但已到货登记”流程，从已有到货日期/箱码候选里选择，不直接进 `No box code`。
- 开箱时箱码扫得出来，但系统没有到货记录：弹窗要求选择到货日期，然后补创建到货记录和箱码文件夹，再正常保存 PO 图片。
- 开箱时箱码确实无法确认：才进入 `No box code`。
- PO code 为空：必须选择备注并上传箱内物品清单/手工清点照片。

### PC Operator

#### PO upload 模块

- `arrival date` 不允许自由输入，必须是下拉栏。
- 下拉栏只显示系统已有的到货日期。
- `PO code` 必须符合 `POMCMP + 6位数字`。
- 格式错误时提示并禁止提交。
- 如果是无箱码补传，必须明确进入 `No box code`，不能进入 `unknown`。

#### Error Record 模块

- `PO code` 必须符合 `POMCMP + 6位数字`。
- 格式错误时提示并禁止提交。
- Error Record 图片进入 `data/uploads/Error PO Paper/` 模块，不混入到货日期文件夹。

## 后端规则

### 1. 普通开箱接口拒绝兜底目录

`/api/unboxing/po`：

- 缺少 `box_code`：拒绝
- `box_code` 像采购单号：拒绝
- `box_code` 无到货记录：拒绝
- `po_code` 格式错误：拒绝
- 不允许写入 `uploads/unknown/`

### 2. PC/管理员补传接口使用明确异常目录

PC 补传或管理员补传可以允许缺信息，但必须明确进入：

- `No box code`
- 带备注的箱码文件夹，例如 `20260501DSH030（配件箱、手工清点）`
- `_needs_arrival_date`（仅管理员补传、确实缺到货日期时）
- `Error PO Paper`（仅错误 PO 模块）

不能进入 `unknown`。

### 3. DB 同步从文件夹生成

同步器应扫描：

```text
data/uploads/<arrival_date>/<box_code>/<po_file>
```

并生成/更新 DB。

异常目录也要被扫描出来，提供给管理员前端展示：

- 待补箱码
- 待补采购单号
- 待补到货日期
- 历史 unknown

## 管理员前端需要补的能力

### 1. 文件夹健康检查

显示：

- 正常文件数量
- 待补箱码数量
- 待补采购单号数量
- 待补到货日期数量
- 历史 unknown 数量
- 文件存在但 DB 不显示数量
- DB 有记录但文件不存在数量

### 2. 异常整理页面

管理员可以在页面里处理：

- 给 `No box code` 文件补箱码
- 给 `NOPO_*` 或带备注的箱码文件夹补采购单号/备注
- 给 `_needs_arrival_date` 文件补到货日期
- 把历史 `unknown` 文件移动到正确结构

所有整理操作都应该实际移动/重命名文件，然后 DB 跟着同步。

### 3. 文件路径可见

管理员前端展示 PO 照片时，应显示真实路径，例如：

```text
2026-05-12/20260407DSH061/POMCMP030456_20260407DSH061_20260513_101337.jpg
```

这样即使前端信息有 bug，也能回到文件夹定位。

## 第一阶段改造范围

为了避免一次改太大，第一阶段先做：

1. 后端禁止普通开箱上传进入 `unknown`。
2. 员工前端增加箱码/采购单号防呆提示。
3. 增加明确异常目录/命名：
   - `No box code`
   - `NOPO_*` + 箱码/文件名备注
   - `Error PO Paper`
4. 管理员前端增加异常文件入口的基础展示。
5. 保留历史 `unknown`，但新数据不再写入。

## 第二阶段改造范围

1. 管理员前端支持一键整理异常文件。
2. 文件夹健康检查。
3. 历史 `unknown` 半自动整理。
4. DB 与文件夹差异报告。

## 关键判断

这次改造不是“让 DB 更聪明”，而是：

> 让系统围绕文件夹结构工作，让文件夹永远可被人类理解和修复。
